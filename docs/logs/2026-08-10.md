# 工作台标签页复用逻辑 + 移除工具页页脚

## 背景与目标

用户提出两项前端修改：

1. 左侧卡片列表点击工具时不再无条件新增标签页：仅当当前活动标签页有任务（已上传文件 / 处理中）时才新增；无任务时关闭上一个标签页、直接显示新工具。
2. 删除所有工具页面底部相同的页脚区块（logo、「公司」、「法律」、「关注我们」）。

## 变更文件

- `src/js/workbench.ts`
  - `openTab` 新增复用逻辑：点击工具卡片时，若 `activeTabId` 存在且与目标工具不同，先用既有 `isTabBusy` 检测活动标签页；空闲则 `destroyTab` 关闭，再 `openPage` 打开新工具；有任务则保留并新增标签页。
  - 重复点击同一工具仍走 `openPage` 内的 existing 分支，只激活已有标签页，行为不变。
  - 更新文件头注释，说明新的标签页语义。
- `src/pages/*.html`（115 个工具页面）
  - 用 `sed -i '/^ *{{> footer }}$/d'` 删除统一的 `{{> footer }}` 引用行，每页各 1 行。

## 决策

- 页脚只从工具页移除；根目录静态页（`about.html`、`contact.html`、`licensing.html`、`privacy.html`、`terms.html`、`404.html`）仍保留 `{{> footer }}`，未改动 `src/partials/footer.html` 与 `footer-simple.html`。
- 复用逻辑只作用于工具卡片入口（`openTab`，含首页 `data-open-tool` 快捷入口）；静态页标签（关于/联系/许可）的打开逻辑不变。

## 验证

- `node node_modules/typescript/bin/tsc --noEmit`：通过，exit 0。
- `node node_modules/vite/bin/vite.js build`：构建成功。
- 构建产物检查：`dist/merge-pdf.html` 无 `<footer`、无「Follow Us/关注我们」内容；`dist/about.html` 仍保留页脚；`dist/index.html` 首页本就不含页脚。

## 已知警告与风险

- git 提示修改过的 `src/pages/*.html` 工作副本 LF 将在下次 git 操作时转 CRLF（仓库既有 autocrlf 行为，无实际影响）。
- 未做浏览器端人工回归；标签页复用依赖 `isTabBusy`（`__tuheBusy` 钩子、`#loader-modal`、file input 检测），跨域或加载失败时按空闲处理，与既有关闭确认逻辑一致。

# 标签页替换动画优化：原位替换消除跳动

## 背景与目标

标签页复用上线后，频繁点击左侧卡片时可见明显跳动：旧标签走 `wb-tab-out` 收起动画延迟 180ms 移除，新标签追加到标签条末尾再"移动"到第一个位置。需要更美观的替换方式。

## 变更文件

- `src/js/workbench.ts`
  - `openPage(page, replaceTabId?)` 新增可选参数：传入时新标签用 `old.tabEl.replaceWith(tabEl)`、`old.panelEl.replaceWith(panelEl)` 原位替换旧标签，不走 `closing` 收起动画、不追加到末尾、不做 `scrollIntoView`。
  - `openTab` 改为先算出 `replaceTabId`（活动标签页空闲时），传给 `openPage`，不再先 `destroyTab` 再追加。
- `src/css/styles.css`
  - 新增 `.wb-tab.wb-tab-replace` 与 `@keyframes wb-tab-fade`：替换时标签只淡入（0.18s），取消 `wb-tab-in` 的 translateY 上浮位移；内容面板沿用 `wb-panel-in` 淡入。

## 决策

- 视觉上：标签槽位完全不动，新标签原地淡入，iframe 区域由加载遮罩覆盖并淡入，无任何位移。
- `tabs` Map 顺序在替换后新条目位于末尾（DOM 顺序不变），仅影响 `destroyTab` 关闭活动标签后的兜底激活顺序，可接受。

## 验证

- `node node_modules/typescript/bin/tsc --noEmit`：通过（TSC_OK）。
- `node node_modules/vite/bin/vite.js build`：构建成功，✓ built in 3.79s。

## 已知风险

- 未做浏览器端人工回归；如替换动画仍不理想，可调整 `wb-tab-fade` 时长或改用交叉淡化。

## 调查：中文界面仍显示英文的原因与改造方案

**时间：2026-08-10 16:30**

```yaml
date: 2026-08-10
tags: [i18n, 调查, 中文翻译, 无代码改动]
status: 已调查，待用户确认方案
```

### 背景与目标

用户反馈：项目支持多语言，但选择中文后很多界面仍是英文。用户想直接把文案硬编码翻译成中文，不想接入语言控制代码。本任务仅调查现状并给出方案建议，未修改文件。

### 调查结论

- 项目为 BentoPDF（v2.8.7），i18n 基础设施已完整存在：`public/locales/{lang}/common.json` + `tools.json`，共 21 种语言；运行时经 `src/js/i18n/i18n.ts`（i18next + HttpBackend），构建时经 `scripts/generate-i18n-pages.mjs` 为每种语言生成静态页面。
- 中文语言包本身已完整：common.json 269/269 键、tools.json 881/880 键，仅约 7 个值与英文相同（多为专有名词，如 `ocrPdf.name`）。
- 英文残留的真正原因：`src/pages/*.html` 与根目录若干 HTML 中存在大量**硬编码英文文案，未加 `data-i18n` 属性**，粗略统计约 251 处、分布在 53 个文件；另有少量 TS 提示文案硬编码（约 5 处起，多行调用未完全统计）。`applyTranslations()` 只替换带 `data-i18n` 的元素，硬编码文案不会被翻译。
- 关键风险：`src/pages/*.html` 是所有 21 种语言生成页面的**共同母版**，直接在其中硬编码中文会让 de/fr/ja 等所有语言页面都变成中文，并破坏 SEO 多语言静态页。

### 方案建议（已提交用户确认）

1. 推荐：保持 i18n 架构，把中文译文写进 `public/locales/zh/*.json`（en 作 fallback），HTML 元素补 `data-i18n` 属性。翻译工作量与硬编码相同，接线仅为每处加一个属性。
2. 备选（破坏性强）：若确定只做纯中文站，则移除 i18n 构建步骤与语言切换器后硬编码中文，放弃其余 20 种语言与多语言 SEO。

### 执行的命令与验证

- `node -e` 对比 `public/locales/en` 与 `public/locales/zh` 的 JSON 键集合：缺失键 0。
- `grep -oE ">[^<>]*[A-Za-z][^<>]*<"` 统计硬编码英文文本节点：约 251 处 / 53 文件。

### 后续工作

- 等用户确认方案 1 或 2；若选方案 1，按页面分批补齐 `data-i18n` 与 zh/en 文案键，并运行 `npm run build` 验证生成的 `/zh/` 页面。
