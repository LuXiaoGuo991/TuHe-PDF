# ADR 0003：Design Token 渐进迁移策略

- **状态**：Accepted
- **日期**：2026-08-12

## 背景

TuHe PDF 既有页面同时使用 Tailwind utility、自定义 CSS 与少量内联状态样式。直接全局替换 `gray-*`、`indigo-*` 或十六进制颜色，无法判断颜色的真实语义，容易把主操作、危险操作、信息提示和装饰色错误地归为同一种颜色，并可能破坏尚未迁移工具的既有行为。

## 决策

采用两层渐进迁移：

1. **Token 层**：在 `src/css/styles.css` 集中定义画布、表面、边框、文字、操作、焦点和状态色。业务样式不得复制这些颜色值。
2. **组件类层**：通过 `.ui-panel`、`.ui-input`、`.ui-button-*`、`.ui-status-*` 等语义类表达用途。页面迁移时按组件职责替换，而不是按旧颜色字符串替换。

迁移期间允许 Tailwind utility 与 `.ui-*` 类并存：utility 负责布局、间距、尺寸和响应式规则；`.ui-*` 负责颜色、边框、焦点、交互状态与共享视觉。若 utility 与语义类冲突，应删除颜色类而保留布局类。新增代码不得引入 `gray-*`、`indigo-*` 等旧视觉颜色类。

批量脚本只处理可确定的上传区、按钮和输入控件模式；复杂状态、弹窗与预览区必须人工复核。每批迁移均需通过翻译检查、构建和浏览器截图验证。

## 后果

- 新旧页面可分批迁移，不阻塞功能发布。
- 主题调整集中在 token，组件状态更易审计。
- 共存期会保留部分旧样式，需以 ROADMAP 批次逐步清理。
- 自动迁移不能代替语义判断和视觉验收。
